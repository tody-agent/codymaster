# Proposal: Consolidate CodyMaster v6 Into a Lean Kernel With Optional Bridges

Generated by: cm-brainstorm-idea
Date: 2026-04-18

## Why we're doing this

### Qualified Problem

**For:** CodyMaster maintainers and power users who rely on the kit for repeatable agent workflows  
**Who:** need a product that stays lightweight, understandable, and trustworthy as the skill catalog and orchestration features grow  
**The:** current CodyMaster runtime is a capable TypeScript CLI + MCP + skills system  
**That:** already contains most of the right ideas, but still exposes too much surface area across root-level modules, overlapping MCP tools, and partially converged product stories after the OpenSpace/OpenViking experiments  
**Unlike:** a heavy “all-in-one agent platform” that embeds every capability directly, CodyMaster wins when it stays small at the core and delegates specialized intelligence outward  
**Our approach:** finish the simplification arc, collapse duplicate surfaces, and add only narrow bridge capabilities that clearly reduce work for agents and maintainers

### Assumptions From Current Context

1. **Target users:** AI coding operators, maintainers, and advanced builders using CodyMaster in terminal/IDE workflows.
2. **Primary pain point:** the product is directionally strong, but parts of the runtime and docs still feel broader than the actual supported core.
3. **Business goal:** make CodyMaster easier to adopt, easier to maintain, and safer to scale toward 100+ skills without token waste or architectural drift.
4. **Constraints:** stay TypeScript-first, avoid heavy runtime dependencies, preserve backward compatibility where cheap, and prefer deleting code over adding frameworks.
5. **What has already been tried:** OpenSpace-inspired evolution patterns were adopted selectively; OpenViking was trialed and then removed from the actual backend path.

### Evidence From The Current Repo

- `package.json` is currently at **v5.1.0** with a small runtime dependency set and a green quality gate.
- `npm run test:gate` passes on **2026-04-18** with **30/30 test files passing** and **226 passed / 16 skipped tests**.
- `src/` contains **57 files**, with **30 files at the root of `src/`**, which is a real discoverability and ownership problem even though the codebase is still manageable.
- `src/mcp-context-server.ts` currently exposes **18 MCP tools** and mixes protocol handling, tool registry, memory operations, advisory surfaces, and engineering bridge logic in one module.
- `src/mcp-skills-tools.ts` proves that the `cm_plan` / `cm_review` / `cm_qa` / `cm_deploy` family is mostly a thin hint layer rather than deep business logic.
- `src/storage-backend.ts` already routes legacy `storage.backend: viking` configs back to SQLite; the real Viking backend source has already been deleted.
- `src/skill-chain.ts` already includes smart chain matching, `selectTopSkills()`, and quality-weighted optional step selection, so the routing foundation exists.
- `src/ui/hooks.ts` already has a user profile concept, which means v6 should unify profile concerns rather than invent a disconnected second profile system.
- `.cm/config.yaml` and several docs still mention `viking`, so part of the remaining problem is convergence of story, config, and runtime expectations.

### Root Cause(s)

1. **Architecture drift:** CodyMaster accumulated several good ideas in parallel, but some were added as adjacent surfaces instead of converged modules.
2. **Product/runtime mismatch:** OpenViking removal happened in code first, while config/docs/mental models still carry legacy wording and shape.
3. **Tool duplication:** the MCP layer still exposes overlap and “hint tools” that could be represented more cleanly by URI resolution or consolidated handlers.
4. **Scale pressure:** the skill ecosystem is growing faster than the loading/discovery model is being simplified.

### Impact if NOT addressed

- **Business impact:** CodyMaster becomes harder to explain and differentiate because the promise feels wider than the stable core.
- **User impact:** advanced users and agents spend more time navigating the system than benefiting from it.
- **Technical debt impact:** every new skill or feature adds maintenance cost to an already broad runtime surface.

## What's changing

### Codebase Summary

- **Core runtime stack:** TypeScript CLI, SQLite/FTS5 memory, stdio MCP server, local HTTP dashboard/browse servers
- **Quality baseline:** healthy; refactoring can be test-first instead of stabilization-first
- **Repo size context:** docs are broad (**208 files**), but the actual runtime surface is still concentrated enough to refactor safely
- **Architecture tension:** current code is not “too big” yet, but it is broad enough that continued feature growth will make it expensive quickly

### What the v6 Memo Gets Right

- Do not embed heavy systems that are better consumed as external tools or optional services.
- Reduce MCP duplication instead of adding more narrow tools.
- Keep skill count stable and improve loading/activation behavior before adding new folders.
- Delete dead or transitional code once the supported path is clear.
- Treat `cm://` as a natural multiplexer for durable context and workflow hints.

### What Needs Adjustment Based on The Actual Repo

- The Viking backend cleanup is **already mostly done**. v6 should focus on finishing convergence, not planning a removal campaign that has already happened.
- The real MCP surface today is **18 tools**, not 13. The better objective is to simplify the *meaningful* surface area, not chase an arbitrary raw count.
- A user-profile system already exists in `src/ui/hooks.ts`; new profile work should unify with that instead of creating parallel profile storage.
- Quality-weighted routing already exists in `skill-chain.ts`; the gap is productization, modularity, and stronger context/impact bridges.

## Options Evaluated

### Option A: Finish Cleanup Only

**Approach:** complete the post-OpenViking cleanup, prune duplicate MCP tools, and reorganize files without adding new capabilities.  
**Philosophy:** Tech-first hygiene

**What changes:**
- move root files into clearer modules
- deprecate/remove overlapping engineering bridge tools
- align config and docs with the SQLite-only supported path
- stop at structural cleanup

**Effort:** M (~1.5-2.5 weeks)  
**Risk level:** Low

**Pros:**
- lowest delivery risk
- removes confusion fast

**Cons:**
- does not meaningfully improve code understanding or pre-commit decision quality
- may feel like a cleanup release rather than a forward-looking v6

**Best when:** the main goal is simplification only and maintainers want the smallest possible change set.

### Option B: Lean Kernel + Optional Bridges

**Approach:** consolidate CodyMaster into a cleaner kernel architecture, collapse duplicate MCP surfaces, and add only two or three narrow bridges that clearly reduce manual agent work.  
**Philosophy:** Balanced

**What changes:**
- reorganize runtime code into `core/`, `mcp/`, `servers/`, and `utils/`
- split the MCP monolith into transport + registry + tool handlers
- replace thin engineering hint tools with URI-backed workflow and engineering resources where appropriate
- add an optional code intelligence bridge (`cm_code`) plus an impact-check path
- add a lightweight learner that proposes draft skills from successful chains
- introduce lazy skill activation/profile gating instead of broader default loading

**Effort:** L (~3-4 weeks)  
**Risk level:** Medium

**Pros:**
- materially improves maintainability and agent effectiveness
- honors the “small core, delegate outward” principle
- creates a credible v6 story without turning CodyMaster into a platform monster

**Cons:**
- requires careful migration and backward-compatibility choices
- needs disciplined sequencing so docs and tests move with the code

**Best when:** the team wants one meaningful v6 that is leaner and smarter without becoming heavy.

### Option C: Full Self-Evolving Platform Push

**Approach:** go beyond cleanup and build a larger self-learning runtime with automated skill mutation, more orchestration layers, and broader embedded intelligence.  
**Philosophy:** Ambition-first

**What changes:**
- stronger autonomous evolution flows
- more internal scoring/ranking stores
- richer dashboards and automatic adaptation paths

**Effort:** XL (~6-8 weeks)  
**Risk level:** High

**Pros:**
- strongest “agent operating system” narrative
- highest upside if executed perfectly

**Cons:**
- violates the lean constraint that the current repo context clearly needs
- likely recreates the same integration heaviness CodyMaster is trying to leave behind

**Best when:** the product already has a stable lean kernel and evidence that more autonomy is worth the complexity.

## Recommendation

**Choose Option B: Lean Kernel + Optional Bridges**

### Why Option B

1. It matches the repo's real maturity: the core is already solid, so the highest-leverage move is convergence, not reinvention.
2. It turns existing partial strengths into a coherent product story: SQLite brain, URI resolver, advisory loop, routing, and skills all become easier to reason about together.
3. It improves agent productivity in concrete ways without violating the “no heavy embedded runtime” rule.

### Why NOT the other options

- **Option A:** valuable, but too conservative; it would reduce confusion without unlocking much new leverage for agents.
- **Option C:** overreaches and risks repeating the same complexity trap the OpenViking lesson already warned about.

### Quick-win suggestion

Start with the **convergence batch**:

- split `mcp-context-server.ts`
- prune the engineering bridge duplication
- finish the SQLite-only story in config/docs
- keep all behavior backed by existing tests

That creates immediate clarity before the bridge additions land.

## Recommended Scope For v6

### Workstream 1: Converge The Runtime Topology

**Goal:** make ownership obvious and reduce root-level entropy.

**Moves:**
- keep `src/index.ts` as the root entry
- move business logic into:
  - `src/core/memory/`
  - `src/core/brain/`
  - `src/core/skills/`
  - `src/core/engineering/`
- move transport logic into:
  - `src/mcp/`
  - `src/servers/`
- move generic helpers into `src/utils/`

**Acceptance criteria:**
- root `src/` file count is materially reduced
- no behavior changes required for existing CLI entrypoints
- test suite stays green during the move

### Workstream 2: Simplify The MCP Surface

**Goal:** reduce cognitive load and remove overlap.

**Moves:**
- split `src/mcp-context-server.ts` into:
  - `src/mcp/server.ts`
  - `src/mcp/tool-registry.ts`
  - `src/mcp/tools/*.ts`
- consolidate `cm_search` and `cm_memory_query` into `cm_query` aliases
- retire or de-emphasize thin engineering hint tools where `cm_resolve` can serve durable workflow resources
- keep backward-compatible aliases for one release cycle where cheap

**Acceptance criteria:**
- protocol code no longer knows business details directly
- tool registry is declarative
- overlapping tools are reduced without breaking current clients abruptly

### Workstream 3: Add Narrow Bridge Capabilities

**Goal:** improve agent leverage without embedding heavyweight systems.

**Moves:**
- add `cm_code` as an optional bridge to external code intelligence when available
- add `cm://engineering/impact` or equivalent resolved surface for blast-radius checks
- keep failure mode graceful: unavailable bridge returns guidance, not errors

**Acceptance criteria:**
- zero mandatory new runtime dependency
- bridge tools degrade cleanly
- maintainers can explain the feature in one sentence: “CodyMaster delegates deep code graph work instead of rebuilding it”

### Workstream 4: Make Skill Loading Smarter, Not Bigger

**Goal:** scale the skill catalog without increasing default token cost.

**Moves:**
- add profile-aware lazy activation on top of the existing profile concept
- ensure non-active skills remain discoverable but not eagerly loaded
- add a lightweight learner that drafts a `SKILL.md` recipe from repeated successful chains into a review directory

**Acceptance criteria:**
- no new skill folders are required for v6 itself
- successful chain capture is review-first, not auto-activation
- profile behavior is unified with existing CLI profile/user state instead of split-brain storage

## Delivery Principles

1. **Do not add a runtime dependency unless it replaces a meaningful amount of owned code or maintenance burden.**
2. **Do not add a new MCP tool if a clearer URI resource or handler consolidation solves the same problem.**
3. **Do not add more skill folders for v6. Improve activation, routing, and learning around existing skills.**
4. **Do not keep legacy wording once the supported path is settled.**
5. **Prefer graceful degradation over hidden optional complexity.**
