# Proposal: Remove OpenViking From CodyMaster's Default Product Story
Generated by: cm-brainstorm-idea
Date: 2026-04-17

## Why we're doing this

### Qualified Problem

**For:** AI-agent operators and developers adopting CodyMaster for reliable day-1 productivity  
**Who:** Need fast installation, predictable memory behavior, and docs they can trust  
**The:** OpenViking integration in CodyMaster is an experimental memory backend  
**That:** Currently adds onboarding friction, product confusion, and maintenance burden disproportionate to its real delivered value  
**Unlike:** CodyMaster's proven default stack of SQLite + FTS5 + qmd + code indexes, which already covers current memory needs without extra services  
**Our approach:** Remove OpenViking from the default product promise, stop auto-installing it, and reposition memory around the stable stack first

### Root Causes
1. **Technical:** CodyMaster expects OpenViking REST endpoints (`/write`, `/read`, `/search`, `/abstract`, `/overview`) that the current upstream package does not reliably expose; `docs/architecture/data-and-memory.md` already marks it "not usable in v5.0.0".
2. **Product:** README, README-vi, CHANGELOG, installer, skills, and tests still present OpenViking as a meaningful or even automatic feature, creating a mismatch between promise and reality.
3. **Operational:** Auto-install hooks in `install.sh` and `scripts/postinstall.js` increase install complexity, add Python/pip requirements, and make support harder across environments.

### 9 Windows Analysis Summary

| | Past | Present | Future |
|---|---|---|---|
| **Super-system** | AI tooling tolerated heavy setup for power users | Users increasingly expect "clone → install → run" with minimal local services | Winning agent kits will reduce dependency count and maximize trust in defaults |
| **System** | CodyMaster explored OpenViking as a differentiator for semantic memory | Stable memory already comes from SQLite FTS5, qmd, and structural indexing; OpenViking messaging is now contradictory | CodyMaster should market a simpler, proven memory story and keep extensibility only where it is truly supportable |
| **Sub-system** | `StorageBackend` abstraction created a swap path for alternative backends | `viking` touches config parsing, backend files, tests, docs, install scripts, and marketing copy | Components should either be fully supported or explicitly internal/deprecated; onboarding paths should stay dependency-light |

### Impact if NOT addressed
- **Business impact:** Users will bounce during evaluation because installation feels brittle and the product story feels overstated.
- **User impact:** New adopters may waste time trying to enable a backend that docs elsewhere already say is not ready.
- **Technical debt impact:** Every release must keep docs, tests, and install flows aligned with an integration that is not core to current value delivery.

## Recommendation

### Choose Option B: Product De-scope + Technical Deprecation

This gives CodyMaster the fastest path to clarity without forcing a risky all-at-once deletion. It aligns product messaging with actual supported behavior, cuts install friction immediately, and preserves a controlled window to either remove or generalize the backend later.

### Why Option B wins
1. **Fixes the trust problem first:** README, CHANGELOG, and installers stop promising something the architecture docs already dispute.
2. **Improves onboarding immediately:** removing OpenViking from default install paths returns CodyMaster to a Node-first setup with fewer environmental failure points.
3. **Preserves optionality:** the backend abstraction can stay temporarily while maintainers decide whether to fully delete `viking` or replace it with a more realistic generic remote-semantic backend later.

### Why not the other options
- **Option A:** Correct direction long-term, but deleting code/tests/config/docs in one move risks unnecessary churn unless the team is ready to break or migrate all references now.
- **Option C:** Still leaves CodyMaster carrying support and messaging cost for a feature that already weakens install confidence.

### Quick-win suggestion

Start with the **product-layer rollback**:
- remove auto-install from `install.sh` and `scripts/postinstall.js`
- rewrite README / README-vi / CHANGELOG claims
- mark `storage.backend: viking` as deprecated experimental, not recommended

That alone captures most of the user-value of this initiative before any deeper code removal.

## Proposed rollout

### Phase 1: Restore product truth
- Remove OpenViking as a "core feature" from README, README-vi, showcase docs, and comparisons
- Update CHANGELOG to clarify historical work vs current support status
- Align installation docs around `npm ci` / `npm run build` / `npm run test:gate:kit`

### Phase 2: Reduce installation complexity
- Remove OpenViking auto-install from `install.sh`
- Remove OpenViking auto-install from `scripts/postinstall.js`
- Remove first-run guidance that implies Python/pip setup is part of the normal CodyMaster path

### Phase 3: Deprecate technical surface
- Mark `storage.backend: viking` as deprecated experimental in config templates and skill docs
- Add runtime warning when `viking` is selected
- Re-scope tests so CI no longer presents OpenViking as a supported path

### Phase 4: Cleanup remaining legacy surfaces
- Remove stale OpenViking messaging from any remaining product-facing landing/docs content
- Keep historical/internal records only where they are clearly archival and not part of the active product story
- Reassess whether backend source removal is still needed after product-facing cleanup is complete
