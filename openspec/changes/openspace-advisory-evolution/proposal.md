# Proposal: Complete the OpenSpace-Inspired Evolution Loop in CodyMaster

Generated by: cm-brainstorm-idea
Date: 2026-04-17

## Why we're doing this

### Qualified Problem

**For:** CodyMaster maintainers and power users who want the kit to become measurably smarter over time  
**Who:** already have Smart Spine memory, skill routing, telemetry tables, and an `ExecutionAnalyzer`, but still cannot use them as a complete operator-facing improvement loop  
**The:** current OpenSpace-inspired architecture in CodyMaster is a partial subsystem  
**That:** captures execution signals but does not yet convert them into ranking improvements, clear review surfaces, or guarded FIX / DERIVED / CAPTURED workflows people can actually run  
**Unlike:** `uprade_openspace.md`, which describes a broad self-evolving brain from scratch, the repo now already ships important foundations and mainly needs productization, orchestration, and safety shaping  
**Our approach:** turn the existing telemetry + analyzer foundation into a complete advisory loop first, then add narrow, operator-invoked evolution actions only where evidence is strong

### Root Cause(s)

1. CodyMaster now has `execution_analyses`, `skill_metrics`, and `src/execution-analyzer.ts`, but these are still infrastructure-level primitives, not a polished workflow.
2. The current self-healing skill family (`cm-skill-health`, `cm-skill-evolution`) is mostly procedural/documentary and is not yet wired to the analyzer outputs in a first-class way.
3. `selectTopSkills()` still scores mainly by relevance, so the system does not yet feed measured execution quality back into routing.

### Evidence from current repo

- `src/execution-analyzer.ts` persists advisory outputs and computes `FIX`, `DERIVED`, and `CAPTURED` recommendations.
- `src/context-db.ts` already stores `execution_analyses` and `skill_metrics`.
- `test/execution-analyzer.test.ts` verifies FIX and CAPTURED advisory behavior.
- `src/skill-chain.ts` already ships `selectTopSkills()` and dynamic chain trimming.
- `src/mcp-context-server.ts` already ships `cm_memory_write` and `cm_natural`.
- `cm-skill-health` and `cm-skill-evolution` already exist as operator workflows.

## What's changing

### Options Evaluated

### Option A: Full Autonomous OpenSpace Port

**Approach:** Build the entire self-evolving runtime now: analyzer, ranking engine, automatic skill mutation, lineage DAG, and fully autonomous FIX / DERIVED / CAPTURED actions.  
**Philosophy:** Tech-first

**What changes:**

- Add a full `SkillStore` and mutation pipeline
- Teach the system to auto-patch or auto-derive skills without operator approval
- Extend CLI and possibly dashboard around autonomous evolution

**Effort:** XL (~5-8 weeks)  
**Risk level:** High

**Pros:**

- Closest to the raw ambition of `uprade_openspace.md`
- Strongest “self-evolving brain” story

**Cons:**

- High risk of noisy or low-trust mutations
- Requires more benchmark confidence than the repo currently has

**Best when:** CodyMaster already has stable precision metrics proving that analyzer recommendations are reliable enough to trigger code changes automatically.

### Option B: Productize the Advisory Loop

**Approach:** Keep evolution operator-driven, but finish the loop around the existing analyzer: better metrics, ranking feedback, a review/report surface, and explicit FIX / DERIVED / CAPTURED workflows.  
**Philosophy:** Balanced

**What changes:**

- Extend the current telemetry + analyzer path into a visible operator workflow
- Feed quality signals back into skill routing
- Add a reviewable CLI surface for recommendations and history

**Effort:** M (~2-4 weeks)  
**Risk level:** Medium

**Pros:**

- Reuses what the repo has already built
- Converts infrastructure into clear product value fast
- Keeps human review in the loop where trust still matters

**Cons:**

- Less flashy than full autonomy
- Still needs a second phase before CodyMaster can claim strong auto-evolution

**Best when:** The team wants visible intelligence gains without destabilizing the current kit.

### Option C: OpenSpace Workbench Only

**Approach:** Focus just on operator tooling: dashboards, summaries, compare views, and reporting over existing metrics without touching routing or evolution behavior yet.  
**Philosophy:** Design-first

**What changes:**

- Add report surfaces for execution analyses and per-skill metrics
- Improve visibility, not behavior

**Effort:** S/M (~1-2 weeks)  
**Risk level:** Low

**Pros:**

- Fastest path to transparency
- Useful for debugging and internal trust-building

**Cons:**

- Does not actually close the loop
- Risks becoming another observability pane without system learning

**Best when:** The team primarily needs visibility and demo-ready reporting before changing orchestration.

## Recommendation

**Choose Option B: Productize the Advisory Loop**

### Why Option B

1. It matches the repo’s real maturity: the telemetry backbone and analyzer already exist, but the usable loop does not.
2. It creates immediate user value by connecting analyzer output, routing, and operator workflows.
3. It keeps trust high by making FIX / DERIVED / CAPTURED reviewable before any future automation.

### Why NOT the other options

- **Option A:** too much autonomy too early; likely to create hard-to-explain mutations and support burden.
- **Option C:** improves visibility but leaves the “learning loop” unfinished.

### Quick-win suggestion

Start by shipping a single command family around the analyzer, for example:

- `cm skill health report`
- `cm skill evolve --advice`
- `cm skill metrics`

That gives operators a concrete OpenSpace-style loop before any auto-editing exists.

## Proposed scope

### Phase 1: Make the Analyzer Visible

- Add a CLI/report surface for recent `execution_analyses`
- Show:
  - task outcome
  - advisory recommendation
  - confidence
  - target skills
  - recent `skill_metrics`
- Reuse `.cm/context.db`; do not add a second database

### Phase 2: Feed Quality Back Into Routing

- Upgrade `selectTopSkills()` so it can combine:
  - relevance
  - mandatory-step priority
  - `qualityWeight(skill_metric)`
- Keep a conservative fallback so mandatory and safety skills are never dropped

### Phase 3: Guarded Evolution Actions

- Wire `cm-skill-health` and `cm-skill-evolution` to the analyzer outputs
- Add an operator-facing evolution flow:
  - `FIX`: patch current skill
  - `DERIVED`: create specialized child skill
  - `CAPTURED`: scaffold a new skill from repeated successful patterns
- No silent automatic mutation in this phase

### Phase 4: Benchmarks and Graduation Criteria

- Measure:
  - recommendation precision
  - false-positive rate
  - token savings from quality-weighted routing
  - completion-rate uplift after applying advised fixes
- Only after hitting thresholds should the team consider partial automation

## What `uprade_openspace.md` gets right

- FIX / DERIVED / CAPTURED is still a strong mental model.
- Token efficiency should come from smarter reuse, routing, and learning, not merely larger memory.

- The missing piece is now **productization and feedback integration**, not greenfield architecture.
