## Action 1 — Intelligent Skill Selection

### Problem
`createChainExecution()` (skill-chain.ts:105) loads ALL chain steps into execution.
`feature-development` chain = 6 steps (4 mandatory + 2 optional).
SkillsBench: 4+ skills → +5.9pp. 2-3 skills → +18.6pp. Gap: **-12.7pp**.

### Approach
Add `selectTopSkills(taskTitle, chain, maxSkills=3)` that produces an ordered subset of chain steps.

**Selection logic:**
1. Split mandatory vs optional steps (`optional=false, condition='always'` = mandatory)
2. If mandatory steps ≤ 3 → include ALL mandatory, fill remaining slots with top-scoring optional
3. If mandatory steps > 3 → include ALL mandatory (safety > optimization), log performance warning
4. Score optional steps: count token overlaps between `taskTitle` words and `step.description` words

**Scoring function (inline, no new deps):**
```typescript
function scoreStepRelevance(taskTitle: string, step: ChainStep): number {
  const taskTokens = new Set(taskTitle.toLowerCase().split(/\W+/).filter(t => t.length > 2));
  const descTokens = step.description.toLowerCase().split(/\W+/).filter(t => t.length > 2);
  const overlap = descTokens.filter(t => taskTokens.has(t)).length;
  // Mandatory steps always beat optional — add 100 base score
  const mandatoryBonus = (!step.optional && step.condition === 'always') ? 100 : 0;
  return overlap + mandatoryBonus;
}
```

**Integration point:** `createChainExecution()` calls `selectTopSkills()` before mapping steps to executions. Caller API unchanged.

**Warning log:** When mandatory count > 3, print to stderr:
```
[CodyMaster] Chain "${chain.name}" has ${mandatory.length} mandatory steps (>3).
Performance may be sub-optimal. Consider splitting this chain. (SkillsBench: 2-3 skills = +18.6pp)
```

### Data Flow
```
matchChain(taskTitle) → ChainDefinition (all steps)
                             ↓
             selectTopSkills(taskTitle, chain, 3)
                             ↓
        filtered ChainStep[] (≤3, or all mandatory if >3)
                             ↓
          createChainExecution(chain with filtered steps, ...)
```

## Action 2 — `cm mcp-serve` Command

### Problem
`dist/mcp-context-server.js` exists and works but has no user-facing `cm` command.
Goose integration requires: `{ "cmd": "npx", "args": ["codymaster", "mcp-serve"] }`.
Currently user must know the direct Node invocation path.

### Approach
New file `src/cli/commands/mcp-serve.ts` registers `cm mcp-serve` command.

**Command spec:**
```
cm mcp-serve [--project <path>] [--print-config]

  --project <path>    Project root to pass to MCP server (default: cwd)
  --print-config      Print Goose/Claude Desktop JSON config snippet and exit
```

**Implementation:** Spawn child process pointing to compiled `dist/mcp-context-server.js`:
```typescript
import { spawn } from 'child_process';
import path from 'path';

// Resolve mcp-context-server relative to this file's location
const serverPath = path.join(__dirname, '..', '..', '..', 'dist', 'mcp-context-server.js');
const child = spawn(process.execPath, [serverPath, '--project', projectPath], {
  stdio: 'inherit',  // pipe stdin/stdout/stderr directly — MCP protocol over stdio
});
child.on('exit', (code) => process.exit(code ?? 0));
process.on('SIGINT',  () => child.kill('SIGINT'));
process.on('SIGTERM', () => child.kill('SIGTERM'));
```

**`--print-config` output:**
```json
{
  "id": "codymaster",
  "name": "CodyMaster Intelligence Layer",
  "type": "stdio",
  "cmd": "npx",
  "args": ["codymaster", "mcp-serve", "--project", "/path/to/project"]
}
```

**Registration:** Add `registerMcpServeCommands(program)` import + call in `command-registry.ts`.

## Action 3 — CodyBench v0.1

### Problem
CodyMaster has no benchmark data. "Does it actually work?" → no answer.
Goose published 8 simple evals and gained massive credibility. Same strategy applies.

### Directory Structure
```
codybench/
├── config.json                  # eval configuration
├── suites/
│   ├── tdd-regression.ts        # TDD skill regression catch rate
│   ├── token-efficiency.ts      # Token savings with vs without CM
│   └── memory-retention.ts      # Memory accuracy across simulated sessions
├── runners/
│   └── claude-code.ts           # Claude Code runner (platform adapter)
├── judges/
│   └── automated.ts             # Automated scoring (no LLM call needed for v0.1)
└── reports/
    └── .gitkeep                 # Results written here, gitignored
```

### `config.json` Schema
```json
{
  "version": "0.1.0",
  "platforms": ["claude-code"],
  "evals": [
    { "id": "tdd-regression",   "repeat": 3, "enabled": true },
    { "id": "token-efficiency", "repeat": 3, "enabled": true },
    { "id": "memory-retention", "repeat": 3, "enabled": true }
  ],
  "compare_mode": "with-vs-without-codymaster",
  "output_dir": "codybench/reports"
}
```

### Suite Interface
```typescript
export interface EvalSuite {
  id: string;
  name: string;
  description: string;
  run(ctx: EvalContext): Promise<EvalResult>;
}

export interface EvalContext {
  projectPath: string;
  withCodyMaster: boolean;
  runId: string;
}

export interface EvalResult {
  suiteId: string;
  runId: string;
  withCodyMaster: boolean;
  score: number;       // 0-100
  metrics: Record<string, number>;
  notes: string;
  timestamp: string;
}
```

### `cm bench` CLI Command
```
cm bench [--suite <id>] [--runs <n>] [--output <path>]

  --suite <id>     Run specific suite (default: all enabled)
  --runs <n>       Override repeat count
  --output <path>  Output file (default: codybench/reports/results-<timestamp>.json)
```

## Action 4 — NLI Trigger Words in MCP

### Problem
CodyMaster memory is powerful (5-tier) but requires knowing internal tool names.
Goose Memory uses natural language: "remember X", "forget Y", "find Z".
CodyMaster has no `cm_memory_write` tool (can only decay/query, not write).
Barrier to use: agents must know `cm_memory_decay` instead of just saying "forget this".

### New Tools to Add

**Tool: `cm_memory_write`** — writes a new learning to SQLite
```typescript
interface MemoryWriteArgs {
  content: string;           // What to remember
  scope?: string;            // 'session' | 'project' | 'global' (default: 'project')
  category?: string;         // 'code_pattern' | 'arch_decision' | 'bug_fix' | 'user_pref' | 'context'
  ttl_days?: number;         // TTL (default: 30 for session, 90 for project, 365 for global)
  importance?: 'low' | 'medium' | 'high';  // default: medium
}
```

Implementation: insert into `learnings` table in SQLite (same DB as `cm_query`).
Auto-categorization: keyword matching on `content` to detect category:
- "decided to" / "architecture" / "we chose" → `arch_decision`
- "bug" / "fixed" / "caused by" → `bug_fix`
- "prefer" / "always" / "never" → `user_pref`
- "function" / "pattern" / "approach" → `code_pattern`
- fallback → `context`

**Tool: `cm_natural`** — NLI router that maps freeform text to existing tools
```typescript
interface NaturalArgs {
  text: string;  // Freeform natural language input
}
```

Pattern matching (regex, no LLM call):
```typescript
const NLI_PATTERNS = [
  { pattern: /\b(remember|save|note)\s+that\b/i,          action: 'write',  scope: 'project' },
  { pattern: /\b(remember|save)\s+this\b/i,               action: 'write',  scope: 'project' },
  { pattern: /\bimportant[:\s]+/i,                        action: 'write',  scope: 'project', importance: 'high' },
  { pattern: /\b(forget|remove|delete)\s+(about\s+)?/i,   action: 'decay',  ttl: 0 },
  { pattern: /\b(what\s+did\s+we|what\s+do\s+we)\s+know/i, action: 'query' },
  { pattern: /\b(what\s+did\s+we\s+learn|lessons?\s+learned)/i, action: 'query' },
  { pattern: /\b(search|find|look\s+up)\b/i,              action: 'search' },
];
```

Routing:
- `action: 'write'` → call `cmMemoryWrite()` with extracted content (text after trigger phrase)
- `action: 'decay'` → call `cmMemoryDecay({ dry_run: false })` + targeted decay by keyword search
- `action: 'query'` / `action: 'search'` → call `cmQuery()` with extracted topic

### Integration in `handleRequest()`
Add `cm_natural` and `cm_memory_write` to both the `TOOLS` array and the `tools/call` dispatch switch.
No changes to existing tools — purely additive.
